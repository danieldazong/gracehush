## Backend / Edge Function Rules

Use Supabase Edge Functions for:

- all AI calls (Gemini)
- Bible text hydration (HelloAO)
- TTS generation
- writes that need the service role
- subscription status sync (RevenueCat webhook)

Never expose secrets in the mobile app.

**Client-safe env vars (EXPO*PUBLIC* only):** Supabase URL (`EXPO_PUBLIC_SUPABASE_URL`) and publishable key (`EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `sb_publishable_…`; the secret and service_role keys never), Clerk publishable key, Google OAuth client IDs and iOS URL scheme, RevenueCat public SDK keys (step 30: `EXPO_PUBLIC_REVENUECAT_TEST_STORE_KEY` for Expo Go and development builds, `EXPO_PUBLIC_REVENUECAT_IOS_KEY` and `EXPO_PUBLIC_REVENUECAT_ANDROID_KEY` for store builds), PostHog's project token and host (step 34: `EXPO_PUBLIC_POSTHOG_PROJECT_TOKEN`, a `phc_…` project token, and `EXPO_PUBLIC_POSTHOG_HOST`, `https://us.i.posthog.com`; a personal API key (`phx_…`) never: it can read and change the whole PostHog account, and the app refuses one in development).
**Server-only secrets (Edge Function env):** `GEMINI_API_KEY`, `GEMINI_MODEL`, `GEMINI_SCREENING_MODEL` (optional, step 21: the crisis screening's own model, `GEMINI_MODEL` when empty), `GEMINI_FALLBACK_MODEL` (optional, step 21 follow-up: every second attempt of the screening and of the reflection goes to it; it screens entries too, so it must pass the screening evaluation first), `GEMINI_THINKING_LEVEL` (optional), `CLERK_ISSUER`, `CLERK_AUTHORIZED_PARTIES` (optional), `GOOGLE_TTS_CREDENTIALS_B64` (optional, step 22: the Text-to-Speech service account's key file as one line of base64; with it and `TTS_VOICE_NAME` both unset, speech is off), `TTS_VOICE_NAME` (optional, step 22: a Chirp 3 HD voice such as `en-US-Chirp3-HD-<Name>`), `TTS_SPEAKING_RATE` (optional, step 22: 0.25 to 2.0), and (step 30) `REVENUECAT_SECRET_API_KEY` (a RevenueCat V1 secret key, `sk_`), `REVENUECAT_WEBHOOK_AUTH` (the webhook's Authorization value) and `REVENUECAT_WEBHOOK_SIGNING_SECRET` (its HMAC signing secret), and (step 31) `CLERK_SECRET_KEY` (the Clerk instance's secret key, `sk_test_` for Development or `sk_live_`: delete-account deletes the person's Clerk user with it, and it can delete any user of the instance), and (step 35, all three or none) `APPLE_TEAM_ID`, `APPLE_SIWA_KEY_ID` and `APPLE_SIWA_PRIVATE_KEY_B64` (a Sign in with Apple key's `.p8` as one line of base64: delete-account ends the person's Apple sign-in with them, and with none set that step is simply off), and (step 38) Scholar's five: `SCHOLAR_ENABLED` (`true` turns Scholar on and anything else is off: no model is called, and a heavy message still gets the written answer; it is read on every request, so switching needs no deploy), `SCHOLAR_SCREEN_FIRST` (`true` writes a typed message's answer only after its screening; anything else writes it at the same time and holds it until the screening says clear), `SCHOLAR_MODEL`, `SCHOLAR_SCREENING_MODEL` and `SCHOLAR_HEAVY_MODEL` (Gemini model names, none written in code: the everyday answers, the screening of every message, and every answer to a heavy moment together with the second attempt of the other two; a missing or malformed one while Scholar is on is a 500 logged as `bad_config:<NAME>`). Until 2026-11-18 there was a sixth, `SCHOLAR_FREE_DAILY_BUDGET` (the ceiling on free messages answered in one UTC day across the project), which is no longer read now that Scholar is part of Pro alone: `secrets unset SCHOLAR_FREE_DAILY_BUDGET` removes it from a hosted project, and its line can go from the local file. `secrets set --env-file` sends every line, so the local file holds `SCHOLAR_SCREEN_FIRST=false` rather than an empty line. And (step 39) the live talk's six: `SCHOLAR_VOICE_ENABLED` (`true` lets a talk start and anything else is off, read on every request: with it off no talk starts and no voice secret is read, a clear turn of a talk already running hears the switched-off line, and a hard-moment turn is still answered), `ELEVENLABS_API_KEY` (the ElevenLabs workspace's key, restricted to ElevenAgents write and Voices read, with Text to Speech and History write (`speech_history_write`) for Listen in the chosen voice, which deletes each reading: production's has all four since the night of 2026-11-19, and development's lacks History write), `ELEVENLABS_AGENTS` (one JSON object on one line, each voice key to the id of that voice's agent, written by `agent_setup.ts`; a missing, malformed or shared id is a 500 logged as `bad_config:ELEVENLABS_AGENTS`, never a silent fallback to another voice), `ELEVENLABS_LLM_SECRET` (what ElevenLabs sends to `scholar-voice-llm` with every turn, stored at ElevenLabs as the agents' custom LLM key), `SCHOLAR_VOICE_SESSION_SECRET` (signs who a talk belongs to and works out each turn's message id; only the server holds it) and `ELEVENLABS_LLM_SECRET_ID` (the id of that workspace secret at ElevenLabs, which only the setup script reads). And since 2026-11-19 Listen's own switch, `SCHOLAR_LISTEN_VOICE_ENABLED` (`true` has ElevenLabs read an answer aloud in the voice the person chose, and anything else keeps Listen in the devotional's Google voice; read on every request, so switching needs no deploy; apart from `SCHOLAR_VOICE_ENABLED`, so either can be switched alone; on only on a project whose key has Text to Speech and History write and whose live Privacy Policy names Listen's readings). The test run's `ELEVENLABS_AGENT_ID` went when `agent_setup.ts` ran with `--write-ids` (2026-11-13): that agent became the default voice's. On a hosted project it is removed with `secrets unset ELEVENLABS_AGENT_ID`, because `secrets set` adds and updates and never removes. Production gets its own values for all of them, never development's. The platform provides `SUPABASE_URL` and the secret key (`SUPABASE_SECRET_KEYS`, or the older `SUPABASE_SERVICE_ROLE_KEY`): never set by hand, and never in the app.

### Gemini connection and credit (active since 2026-10-23)

The Gemini credit is paid and active, so no step has any billing to set up. Every step that calls a model (25, 28, 29, 31, 32 and any later one) uses it as written here.

- **Status.** The project's Gemini key is on the paid tier (AI Studio shows Tier 1, Prepay plan) with **$20 of credits** bought on 2026-10-23 and **auto-reload off**. Google's paid-services terms apply (see the Gemini API terms note), so a real person's prayer may be sent to it, through the Edge Function only (step 25 onwards). Verified on 2026-10-23: calls served on three models; the timings and the screening evaluation are in the Google billing log entry.
- **The key.** One secret, `GEMINI_API_KEY` (an `AQ.` auth key), server-side only: in `supabase/functions/.env.local` (git ignores it) and in the hosted project's secrets. It never goes in the app, in an `EXPO_PUBLIC_*` variable, a committed file, a log, a test or a chat, and nobody prints it. The credit belongs to the billing account, so any key of the project spends it. The user sets the hosted secrets and deploys (`npx --yes supabase@2.121.0 secrets set --env-file supabase/functions/.env.local --project-ref <project-ref>`, then `functions deploy <name> --project-ref <project-ref> --use-api`); the implementer never holds a management token. `secrets set --env-file` sends every line of the file, so no secret in it may be empty.
- **The models.** `GEMINI_MODEL=gemini-3.1-flash-lite` in the local file and on the hosted project; `GEMINI_FALLBACK_MODEL=gemini-3.8-flash` in the local file and on the hosted project (since 2026-10-30, the user's choice in step 32: it came closest to the tone evaluation's bar and passed the crisis evaluation again that day, 15 of 15 crises and 0 of 15 false alarms; `gemini-3.5-flash-lite` before, which wrote devotionals too short for the tone bar); the local file holds the same values as the hosted project so that `live_check.ts` runs as production does and `secrets set --env-file` sends them again. `GEMINI_SCREENING_MODEL` and `GEMINI_THINKING_LEVEL` empty (the screening uses `GEMINI_MODEL`, and thinking is `low`). No model name is written in code. Changing a model is the user's decision (step 32's tables are in its log entry), and a new screening or fallback model must first pass `run_eval.ts` and the tone evaluation (`run_tone_eval.ts`).
- **The only code that calls Google** is `supabase/functions/process-entry/gemini.ts` (the Interactions API, the key in the `x-goog-api-key` header, `store: false`, retries with backoff). A new function or step that needs a model imports it and the screening in `_shared/safety/`: never a second client, and never a call from the app, which only sends its Clerk session token to an Edge Function (step 25).
- **Check the connection** (made-up text only). The quickest check is `npx --yes deno@2.9.6 run --no-lock --node-modules-dir=none --config supabase/functions/process-entry/deno.json --allow-net --allow-env --allow-read --env-file=supabase/functions/.env.local supabase/functions/process-entry/live_check.ts --shape`: it sends two requests and must print `screening: HTTP 200` (1 to 3 s). `live_check.ts` without `--shape` runs the whole flow on made-up entries, and the screening evaluation is `run_eval.ts` (see Linting and Validation).
- **When a call fails.** HTTP 402 `RESOURCE_EXHAUSTED`, "Your prepayment credits are depleted", means the balance is $0 and every key of the billing account has stopped: `gemini.ts` logs `gemini_http_402:RESOURCE_EXHAUSTED`, never retries it, and the entry fails with `AI_UNAVAILABLE`. Stop, say so, and tell the user to buy credits (aistudio.google.com/billing, **Buy credits**); do not loop. A 429 or a 5xx (busy) is retried by `gemini.ts` with backoff. A 400 is a bad request body, and a 401 or 403 a wrong or revoked key (the user makes a new one and updates both places).
- **What it costs.** At the prices of 2026-10-23 a crisis screening costs about $0.0003, a written reflection about $0.0013 (`gemini-3.1-flash-lite`) to $0.0026 (`gemini-3.8-flash` until 2026-12-31), a three-minute spoken entry about $0.0065 and the 30-case evaluation about $0.01. So $20 is thousands of reflections, and a loop or a large batch is the only way to spend it fast: tell the user the cost before anything that would spend more than about $1.
- **What it does not pay for.** Cloud Text-to-Speech (step 22) is paid by the Cloud Billing account (a Paid account holding the user's $30 credit; its first million characters each month are free), not by the Gemini credit. Supabase and Clerk have their own plans.
- **Ask first.** Never buy credits, change the billing account or plan, or switch auto-reload on for the user: it is their money. Before launch the user turns auto-reload on with a monthly charge limit, because an empty balance stops every key at once. Real people's text reaches Gemini only through the app and the Edge Function; checks, evaluations and tests send made-up text only. The billing account id, a card's digits and the Google Cloud project id never go in a committed file.

### `process-entry` requirements

The function did not exist before step 19 (the architecture notes spoke of a "working draft", but none was ever in this repo), so these were built in, not fixed. Each stays a requirement for every change to the function; the step that finished it is in brackets.

1. **Verify the JWT signature** (step 19, `_shared/auth.ts`). Against the public keys of the Clerk instance, RS256 only, with `iss`, `exp` and `sub` required, a `sid`, the top-level `role` equal to `authenticated`, a session that is not `pending`, and `azp` checked when `CLERK_AUTHORIZED_PARTIES` is set. The user id used anywhere comes only from this result. The app sends Clerk's normal session token: there is no template and no shared secret.
2. **Scope every service-role query** (step 19, `lifecycle.ts`). The service role bypasses RLS, so every query on `journal_entries` and `daily_affirmations` filters by the verified `userId` (a test fails on one that does not), and a `user_id` in the request body is never read.
3. **Validate input** (step 19, `validate.ts`). A POST of at most 64 KB; a lowercase UUID v4 `clientEntryId`; text of 10 to 5,000 characters; or a recording of 3 to 302 seconds, at most 12 MiB, at exactly `{userId}/raw/{clientEntryId}.m4a`; no audio in the body. The entry reaches the model inside `<journal_entry>` tags, with any such tag the person typed removed, and the instruction says everything in it is content and never instructions.
4. **Enforce structured output** (step 19, `schema.ts`, `gemini.ts`, `output.ts`). The schema asks; `output.ts` checks every value and every limit again, cleans the text (no tags, no emoji, curly apostrophes, no "Amen" in the stored prayer) and truncates nothing. At most nine model calls per request (four for the crisis screening, four for the reflection and, step 20, one for a replacement passage): a busy service is tried again after about 2, 4 and 8 s and an unusable reply once more (the vendor note on heavy demand). The screening ends 60 seconds after the request started, and every call 90 seconds after it. Since step 32 `output.ts` also holds the tone's hard checks (`tone.ts`, Pastoral Tone Rules): a verse reference in the devotional or the closing prayer, a phrase of the never-say list, and a word the person capitalized in the middle of a sentence in the title or a headline; a headline is at most 50 characters and a devotional at most 220 words. A retry after a tone failure carries a `<correction>` note that names the rule (and, for a private word, the words to avoid), and a reply whose only fault is a private word is kept with safe texts in its leaking fields when no clean reply comes. Since gen-v2.2 (2026-10-31) the hook guard runs last: a devotional that begins with a stock opening, with a first word one of the person's recent devotionals began with, or with a first sentence over 16 words is asked for once more with a note, and kept as it was when no better reply comes (Pastoral Tone Rules). Since gen-v2.3 (step 36) four more soft checks run after the private-word check and before the hook guard: the prayer's voice, grounding, the validation line and the echo. Each sends a correction note and keeps a salvage, and none ever fails a reflection (Pastoral Tone Rules).
5. **Run crisis screening first** (step 21, built in `_shared/safety/`; the rules are under Crisis Screening Rules). Nothing is made for an entry that was not screened. The order is: claim, read the recording, screen, then (step 22) the free-tier limit, then the reflection from the screened words. A heavy moment (gen-v2.4, 2026-11-08) skips the limit, so it is never paywalled or counted, and is written in full by the heavy rules, with the written fallback when no reply can be had (Crisis Safety Rules). A content block makes a heavy moment and is never an error shown to the person, so there is no `CONTENT_BLOCKED` code.
6. **Hydrate scripture exactly** (step 20, `_shared/bible/` and `process-entry/scripture.ts`). The model returns only where a passage is: a USFM book id from the 66-id list (a schema enum built from `books.ts`, the one list), the chapter and the verses. The server checks that shape against the book table, reads the chapter from the Free Use Bible API (the Berean Standard Bible only, in the simplified format), repairs the spacing the API gets wrong (whitespace only: not one letter or mark changes), joins the verses (a line break where either neighbour is poetry, a space otherwise) and stores the text with `scripture_verified` true. A passage that does not exist (a chapter or a verse the BSB lacks, more than six verses, or more than 1,200 characters) costs one small follow-up request that sees the reflection's title and feeling and never the person's words; if that fails too the reflection is saved with no passage. A chapter that cannot be read (the API down, slow or answering with something else) is not a wrong passage: the reference is kept with no text and `scripture_verified` false, and `confirm-scripture` checks it again later. A heavy moment never gets a passage from `DENIED_PASSAGES` (`heavy.ts`): one is replaced by the follow-up request, and a heavy moment left with none gets Isaiah 41:10 (`HEAVY_FALLBACK_PASSAGE`), read from the Bible like any passage. Otherwise there is no fallback verse, nothing is typed or recalled by the model, no verse is ever hardcoded, and the devotional never quotes scripture.
7. **Keep storage private** (decided and built in step 18). `journal_media` is a private bucket (25 MB, audio types only) with one folder per user. The database stores object paths (`audio_path`, `devotional_audio_path`), never URLs, and the app gets short-lived signed URLs (step 22), which it uses once to download the file (step 26). The app may read its own folder and upload only into `{userId}/raw/`; the Edge Function writes `{userId}/devotionals/` through the service role.
8. **The raw audio is saved before the function is called.** The app uploads it to `journal_media` first (step 23); the function only reads it, and a failed run keeps the file and the text.
9. **Reminder times** are not needed on the server: the phone schedules the notifications from the profile (step 28), and `daily_affirmations.scheduled_for` stays unset. Nothing in the function hardcodes 08:00, 13:00 or 20:00.
10. **Enforce the free tier server-side** (step 22). Free users get 3 devotionals a week (`FREE_DEVOTIONALS_PER_WEEK` in `_shared/limits/constants.ts`, mirrored in `src/constants/app.ts`); a trial or Pro account has no limit. The check goes after the crisis screening and before the model call that writes the reflection. The week runs from Monday 00:00 to the next Monday on the clock of the profile's time zone (`_shared/limits/weekly.ts`, `Intl` only; a zone `Intl` does not know is read as UTC and logged). An entry counts when it is not a heavy moment (`is_crisis`) and it has its script, and so does an entry still being made that was claimed earlier than the one being checked (so two requests at once cannot both be the third and the fourth); a heavy moment, a failed one and the entry being checked itself never count. Since step 29b a devotional that was deleted still counts for the week it was made in: `delete-entry` records it in `deleted_devotionals` (an id, the owner and when it was made) before it deletes the reflection, and the check adds this person's records made from the week's start, so deleting a reflection does not give a free one back (a failing records query is `db:limit_deleted`, a 500). `checkDevotionalLimit` asks its three questions together (one round trip to a far database, not three), and two entries are put in order by their creation time to the millisecond, the larger id coming later. Over the limit the entry is saved as failed with `LIMIT_REACHED` (an audio entry keeps its transcript) and the answer is a 402 whose body also carries `entryId` and `usage` (`used`, `limit`, `resetsAt`), which opens the Paywall; a heavy moment is never counted or blocked. Known limit: the count is by when an entry was created, so a free account's blocked entry from an earlier week that is sent again later is made and not counted (counting by when it was made needs a column, a later migration). A narrower race remains and was left alone: two requests whose entries are created within a millisecond of each other, the later one's row becoming visible only after the earlier one's check, could still both pass; it costs one free devotional and a lock was not worth adding.
11. **Return consistent errors** (step 19, `_shared/errors.ts`): `{ error: { code, message, requestId } }`, the 12 codes and statuses of `ProcessEntryErrorCode`, with the messages from one map (`_shared/errors.ts` also holds `NOT_FOUND`, 404, which only `confirm-scripture` and `delete-entry` answer: each function's contract lists its own codes). The 402 also carries `entryId` and `usage` beside `error` (step 22, `AppError.details`: values the function built itself, never logged). Never a stack trace, a provider's words, SQL or anything the person wrote.
12. **Long work.** One request does it all: the model calls end by 90 seconds, the platform stops a function at 150 (free plan), and a claim lapses after 3 minutes so a request that died can be sent again. Since 2026-11-09 the answer goes out as soon as the reflection and its affirmations are saved (about 10 to 30 seconds), and speech (requirement 13) runs behind it through `EdgeRuntime.waitUntil` (Supabase's Background Tasks), under the same budget: it starts only in the first 100 seconds of the request, its Google calls end by 135 and its upload by at most 5 seconds after that (`speechTiming` in `process-entry/constants.ts`), and the platform keeps the worker alive for it after the response. The owner asked for a processing screen of about three seconds (first four, on 2026-11-09), which made the background job the right restructuring (until then speech ran before the answer, which went out by about 145 seconds when everything was slow).
13. **Speak the devotional** (decided in the step 22 review, built in step 22; `_shared/tts/`). Speech is a best-effort step after the reflection is saved as `ready`, so nothing about it can lose a reflection. Since 2026-11-09 it runs behind the answer: `speakThenRespond` in `handler.ts` asks `planSpeech` (the secrets, the time budget, the script) whether to speak, puts `background` in the request line's `tts`, answers, and runs `speakBehind` (the stage, then a second log line with the same `requestId` and `reason: "speech"`) inside `EdgeRuntime.waitUntil`; a project with speech off or half set up answers with the stage's own skip word as before. So no answer carries an audio path: the app shows the text at once and picks the audio up when the row changes (Realtime's `entry_changed`, or the hook's reads). A worker the platform ends before the background task finishes leaves a reflection with no audio and no `TTS_FAILED`: the app shows "audio pending" for AUDIO_PENDING_MS and "text only" after, and the same request sent again, or the speech-only retry below, adds the audio. The script is built on the server from the saved devotional (`script.ts`): the paragraphs (nothing before them: the devotional's first sentence is its hook and the first thing heard, with no fixed line and no title since 2026-10-31, Pastoral Tone Rules), the passage with a spoken reference only when `scripture_verified`, and the closing prayer ending in "Amen."; every field is cleaned first, and a tag or a bracketed span is removed together with what is inside it, so the model cannot add a pause or a sound; over 4,800 bytes the passage goes first, then the prayer, and the devotional is never cut. Cloud Text-to-Speech reads it (Chirp 3 HD, `markup`, `LINEAR16`: a lossless WAV since 2026-10-24, see its vendor note), the function reads the length from the WAV's header (`wavDuration.ts`) and saves it as `{userId}/devotionals/{entryId}.wav` (`audio/wav`, about 48 KB a second) in `journal_media` (service role, replacing any earlier file), storing only the path and the duration. **No URL is returned or stored:** the app asks Supabase for a link of its own (`createSignedUrl(path, 300)`, allowed by the bucket's select policy for its own folder), uses it once to download the file to the phone (step 26) and never keeps it. A failure leaves the entry `ready` with no audio (and `error_code` `TTS_FAILED` when a call failed, cleared when audio is added later); with no speech secrets set the step is simply off. A retry of a finished entry that has its devotional and no audio runs speech only (no screening, no limit, no model call), and its update only fills an empty audio path, so two retries cannot both win. The stage is `process-entry/speech.ts` (`speechStage`: it never throws and returns the entry as it now stands, with the log words), and a refusal by Google or Storage is marked with `markSpeechFailed`, guarded like `saveAudio` (a ready reflection with no audio, never one with no devotional, and it returns the marked row; since 2026-11-09 the answer no longer carries the speech's result, which the second log line and the row's `error_code` do). Ambient sound is never mixed in on the server. The log holds one word about speech (`tts`) and numbers, never the script, the verse or a link.
14. **Read each affirmation's verse exactly** (step 37, `process-entry/verses.ts`). After the passage, each affirmation's verse is read from the Bible like the passage (requirement 6), with the rules of Pastoral Tone Rules ("A verse under each affirmation") and at most one small follow-up request for every verse that breaks one; the server stores the reference and the Bible's own words in `daily_affirmations.verse_reference` and `verse_text`, both or neither, and never a verse it did not read. A verse is never typed by the model or by code; an affirmation whose verse cannot be found is saved without one. The answer carries each affirmation's `verse` (`AffirmationVerse` in both contract copies) and the log line counts them (`affirmationVerses`).
15. **One more affirmation at a time** (2026-11-09, `add-affirmation`, the owner's request). A finished reflection may hold up to AFFIRMATION_LIMIT (10) affirmations: the three made with it and up to seven the person adds from Reflection, one per request. The function verifies the token like process-entry, finds the caller's own entry (another person's and a missing one are the same 404; one still being made is 409 ALREADY_PROCESSING; a failed one or a heavy moment saved before 2026-11-08 has no reflection to add to, 404), refuses the eleventh with 409 AFFIRMATION_LIMIT, and makes one model call (add-v1, `add-affirmation/prompt.ts`) from the person's entry, the reflection's title, feeling and passage, and the headlines and verses it already has (never their texts), under the same verse and headline rules as process-entry's three (Pastoral Tone Rules, "A verse under each affirmation") and the heavy rules for a heavy moment. The reply's hard checks are a verse reference in the text and a never-say phrase (a heavy never-say for a heavy moment); its soft checks are a word of the person's in the headline (salvaged with a safe headline), a feeling word and a headline the reflection or the person's recent affirmations already have (kept as they are when no clean reply comes). Its verse is read from the Bible like every verse (`resolveAffirmationVerses`, with the one follow-up), never the reflection's passage or a verse the reflection or the person's recent affirmations carry; one still unusable leaves it without one. The row is inserted at the next position with no lock-screen slot (the migration's trigger fills a missing position), and when the model names a time of day the new affirmation fits better than the one carrying it, `feature_affirmation` moves that slot in one transaction, best effort (a failed move leaves the lock screen as it was). The answer is every affirmation of the reflection in position order. Nothing here counts toward the free week, a request a safety filter blocks is 503 AI_UNAVAILABLE ("blocked") and nothing is written, and the model calls end 40 seconds after the request started (`addTiming`; the app gives up at 45).

### Edge Function Rules

- `userId` comes only from `verifyClerkRequest`. Nothing else may supply it.
- One entry per `(user, clientEntryId)`. A retry of a finished entry returns it (no model call, no limit counted); a failed one, or one whose claim has lapsed, is claimed again by exactly one request (a compare-and-set update); one that is running answers 409.
- A reflection is `ready` only after its affirmations are saved: `ready` is the last write of a good run.
- Recordings are read from `journal_media`. No audio travels in a request body.
- `contracts.ts` and `src/types/index.ts` change together. `src/types/contractParity.ts` fails `npm run typecheck` when they differ, and `fixtures/parity.json` is checked against both the function's `response.ts` and the app's `toJournalEntry`.

A talk's turns are saved as spoken messages, so they are also taken out of a later message's thirty in ten minutes: when that count has reached the limit, the engine reads when the person's spoken messages of those ten minutes were made (`listSpokenTimes` in `scholar-turn/lifecycle.ts`) and the person's talks (`listSessionsSince`), and `countTalkTurns` (`_shared/voice/allowance.ts`) takes out the ones made while one of their talks ran, with 5 seconds either side for the two clocks. A talk that never said it ended runs up to now and never past its session's 32 minutes; a spoken message recorded outside any talk, and every typed message, still counts; and a read that fails takes nothing out. The caller may also pass `refuse` (`cap` or `off`): the turn is still screened, and only a turn the screening calls clear is released unanswered, with its words kept (`LIMIT_REACHED` with the reason `voice:cap`, or `SCHOLAR_UNAVAILABLE` with `voice:off`). So a hard moment is answered whatever the cap or the switch, as a typed message's limit comes only after a clear screening.
- `scholar-voice-start` (step 39) starts one live talk. It takes a POST of at most 2 KB, `{ conversationId, voice, entryId?, region? }`, and answers `{ talkId, conversationId, conversationToken, session, voice, heavy, limits }` (`ScholarVoiceStartRequest` and `ScholarVoiceStartResponse` in `process-entry/contracts.ts`, with the app's copy and its line in `contractParity.ts`). `limits` is `{ talkSeconds, monthSecondsLeft, resetsAt }`, and both numbers are null in a heavy conversation. A key the body does not know is `INVALID_REQUEST`, so no user id and no voice id ever travel in a body, and `voice` is one of the eight keys (one the server does not know becomes the default). Its order is fixed: the method, the Clerk token and the body; the two switches, read on every request (`SCHOLAR_VOICE_ENABLED`, then step 38's `SCHOLAR_ENABLED`: `SCHOLAR_UNAVAILABLE` with `voice:off` or `scholar:off`); one read (the profile, whether Scholar is closed for the account, the conversation and its reflection, and the account's talks of the last 32 days); an account Scholar is closed for (`SCHOLAR_ADULTS_ONLY`); the plan (`confirmPaidPlan`): an account that is not Pro is `LIMIT_REACHED` with `usage.kind` `talk_plan` outside its free conversation (since 2026-11-20 it may talk in that one, or in a conversation when none is claimed yet, up to `SCHOLAR_FREE.talkSeconds` (180) over all its talks there, `limits` `{ talkSeconds: what is left, monthSecondsLeft: null }`, after every other check the start claims the conversation with `claim_scholar_free_conversation` and is refused when another one won, and a free account's talk is in `warm` whatever voice it asks), in a heavy conversation too (a free account, and since 2026-11-18 a trial, whose `resetsAt` is the day its plan begins); the conversation, by step 38's rules (a reflection's existing conversation wins, and one opened from a heavy reflection starts heavy); the day's starts (20, then `RATE_LIMITED` with `voice:starts`); the time: a heavy conversation's talk has no cap and costs nothing, up to 120 minutes of heavy talk in a day (then `SCHOLAR_UNAVAILABLE` with `voice:heavy_day`), and any other talk needs at least 30 seconds of the month's 60 minutes (30 until 2026-11-18) (else `LIMIT_REACHED` with `talk_month` and when the time returns); the account's talks that never said they ended, closed at their last activity (one account has one talk at a time); the voice, and ElevenLabs' one-time token for that voice's private agent (ElevenLabs at capacity is `SCHOLAR_UNAVAILABLE`, any other failure `AI_UNAVAILABLE`); the talk's row and its signed session; and, after the response, the deletion of finished talks at ElevenLabs. Nothing is written and no token is asked for until every check has passed, so a refused start costs nothing and counts as nothing. Its codes are the 11 of `ScholarVoiceStartErrorCode`. Its log line is the shared one (43 fields): `reason` `voice:start` or the error's own word, `limit` `pro_ok`, `pro_blocked`, `free_ok` or `trial_ok` (a free conversation's talk, since 2026-11-20), `free_blocked`, `trial_blocked` (since 2026-11-18) or `exempt` (with `:bad_timezone` when the profile's zone was not valid, except on `trial_blocked` and `exempt`) and `limitUsed` the month's seconds used; never the token, the session, the voice, or a conversation or talk id.
- **A talk's signed session** (`_shared/voice/session.ts`). ElevenLabs, not the phone, calls `scholar-voice-llm`, so that function cannot read a Clerk token. `scholar-voice-start` signs who the talk belongs to and what it is about (the user, the talk's row, the conversation, the reflection or none, the phone's region and the voice, with HMAC-SHA256 under `SCHOLAR_VOICE_SESSION_SECRET`, accepted for 32 minutes: ElevenLabs' own 30-minute limit for a talk and two minutes of room), the phone hands the signed value to ElevenLabs as the custom LLM extra body, and ElevenLabs sends it back with every turn. The phone can read it and cannot forge or change it, and nothing ElevenLabs or the phone sends beside it is believed.
- `scholar-voice-llm` (step 39) is Scholar's side of a live talk. ElevenLabs calls it for each turn in the OpenAI chat format and speaks what it streams back (chat-completion chunks as server-sent events, `_shared/voice/sse.ts`); the phone never calls it, and it has no CORS and no Clerk token. Its order is fixed, and it is what keeps a person safe: (1) POST only, and ElevenLabs' shared secret (`ELEVENLABS_LLM_SECRET`, the agents' custom LLM key), compared without an early exit, else 401; (2) the body, at most 256 KB, of which two things are read and nothing else: the person's words since Scholar last spoke, every message of role "user" after the last one of role "assistant", joined in ElevenLabs' order (cut at 2,000 characters; since the walk-through of 2026-11-14, when ElevenLabs listed a heavy sentence before a one-word fragment and reading only the newest message answered the fragment and never screened the sentence), and `elevenlabs_extra_body.session`; ElevenLabs' own prompt, history and tools never reach a model of ours, because the engine reads the conversation from our database; (3) the session: signed by our server, not expired, and its row found for that user and not ended, otherwise Scholar says the ended line and nothing else happens; (4) a turn with no letter or digit in it (a noise) gets the unheard line ("Sorry, I didn’t catch that. Could you say it again?"), and nothing is saved; it can never be answered with nothing, because ElevenLabs takes a reply with no words for a failure and ends the talk at the person's next sentence, so every path of the function says something, a failure of its own included; (5) the phrase list reads the words, and when it does not match and the whole turn is only a stop word (`stop.ts`: "stop", "wait", "hold on", "pause", "one moment", "one second", "just a moment", "be quiet", with "okay", "ok", "please" or "Scholar" around it; and "weight" or "weigh" alone, what ElevenLabs' speech-to-text wrote for a spoken "Wait." on the owner's iPhone, `STOP_HEARD_AS`), Scholar says "Okay, I’ll wait. Say “go on” when you’re ready." ("Okay. I’m here." in a heavy conversation) with no model call, and nothing is saved, and it never goes on by itself; the person's next turn is written with a recap (`afterStop`, read only by the stop-word check from the turn before Scholar's last line, and SPOKEN_RESUME, Pastoral Tone Rules); (6) the talk's cap (its own seconds, or 80 turns) and the voice switch, for a conversation that is not heavy, go to the engine as `refuse` and are never decided here; (7) the turn, whose message id is worked out from the talk, the turn's number and its words (`turnId.ts`: an HMAC under the session secret, shaped as a UUID v4), so a request ElevenLabs sends again finds the same message: it waits for the answer being written or replays the saved one, and nothing is screened, written or counted twice; all of this work runs inside `EdgeRuntime.waitUntil`, so the answer is finished and saved even when ElevenLabs stops listening (the person spoke again, or the attempt was given up); (8) the stream, while the turn runs: a holding line when nothing is ready, sent with sixteen zero-width words after it in the same piece (`stream.hold`, `HOLD_PAD` in `_shared/voice/sse.ts`: a zero-width space and an ordinary space, sixteen times), because ElevenLabs starts speaking only once its buffer holds enough words and keeps the last words back, so a holding line alone was heard only together with the answer, and twelve ellipses, which did the counting too, were voiced by some voices (the vendor note has the measurements); then the answer, from the moment the engine hands it over checked and before it is saved (`onReady`; the save goes on in the background, and an answer heard whose save then fails or runs out of time is logged `voice:unsaved:<why>`), as the sentences of its Listen script (`buildScholarSpeech`: the lead reading, the answer, the supporting reading, a prayer ending in "Amen."), with the help numbers said digit by digit (`sayNumbers`) and the spoken help line last when the answer carries one; (9) when there is no answer: in a heavy conversation, or for words the phrase list matched, the written answer of last resort and the 988 line in their spoken forms (said, not saved: the engine saves what it finishes), never an error and never silence; otherwise the fixed line for what happened (not ready, the cap, switched off, ended) or, for an account Scholar was closed for during the talk, the adults-only answer; (10) after the stream, the talk's row: its last turn, its length, its turns, and heavy when the conversation is. The times are `voiceTiming` (`_shared/voice/constants.ts`): the holding line after 7 seconds for an everyday turn ("Give me a moment to think about that."), and in a heavy conversation after 5 seconds ("I’m here. Give me a moment.") and again after 13 ("I’m still here with you."); an everyday answer has 13 seconds, with one attempt of the writer, and then the person hears the not-ready line and the message is released, as a failed typed message is; a hard-moment answer has 22 seconds, and then the written answer and the help line. ElevenLabs gives an attempt up when no new piece has arrived for 15 seconds (the agents' `cascade_timeout_seconds`, counted from the request's start and from each piece), so no two moments of a turn are that far apart: an everyday turn's are at 0, 7 and 13 seconds, and a hard moment's at 0, 5, 13 and at most 23.5 (`_shared/voice/constants_test.ts` holds them to it, with 2 seconds of room). A holding line is heard about half a second after its moment, and nothing after it but the next words (measured in all eight voices; the ElevenLabs vendor note). The fixed lines are `VOICE_LINES` (`_shared/voice/lines.ts`), each a draft for the readers. Its log line is the shared one (43 fields), written when the turn's work is done, with `inputType` `audio`, `promptVersion` `scholar-v3/spoken-v4` (`scholar-v2/spoken-v4` before 2026-11-16) and one word as its `reason`: `voice:answered`, `voice:heavy`, `voice:emergency`, `voice:fallback:<why>`, `voice:replayed`, `voice:joined` (the engine's own word with "voice" in front), `voice:unsaved:<why>`, `voice:not_ready:<why>`, `voice:cap`, `voice:off`, `voice:adults_only`, `voice:stop`, `voice:unheard` or `voice:ended`; never a word that was said or spoken, an id, a help line or the voice. What a person never hears in a talk: words a model wrote that were not screened, a reading that is not the Berean Standard Bible's own text, an error message, or silence where step 38 promises an answer.
- `scholar-voice-end` (step 39): the phone says a live talk is over. It takes exactly `{ talkId }` and answers `{ limits }`, what is left of the month's talk time, so the app never counts for itself (`ScholarVoiceEndRequest`, `ScholarVoiceEndResponse`). The talk's row gets its end and its length, from its start to this call. What a talk costs the person is decided in `_shared/voice/allowance.ts`: its time, never more than its own cap, and nothing in a heavy conversation. Ending always works: it reads neither switch and needs no voice secret. Another person's talk and one that does not exist are the same `NOT_FOUND`, and calling it twice changes nothing. A talk nobody ended (the app was closed, the connection was lost) is closed at its last turn by the account's next start. Its codes are `INVALID_REQUEST`, `UNAUTHORIZED`, `NOT_FOUND`, `METHOD_NOT_ALLOWED` and `INTERNAL`, and its `reason` is `voice:end`, or `voice:end:no_sweep` when the voice secrets cannot be read, so the deletion below could not run. For an account that is not Pro (2026-11-20) its `limits` are the free conversation's talk time left (`freeTalkLimits`, `monthSecondsLeft` null), never a month.
- **Finished talks are deleted at ElevenLabs** (`_shared/voice/sweep.ts`, step 39). ElevenLabs keeps no recording, but until a talk is deleted it holds the words that were said and a summary its own model wrote, and there is no switch for either. So after the response of every start and every end of a talk, the server lists the talks of its eight agents and deletes each one that has ended (`done` or `failed`), at most 30 a run, five at a time. It never touches a talk that is still running or still being closed, and never anything of another agent in the workspace. After an end the sweep runs again at 10, 20 and 30 seconds while one of our agents still lists a talk ElevenLabs is working on (`endSweepTiming.retryAtMs`, four runs at most; the walk-through of 2026-11-14 found the first run leaving the talk that had just ended, still being closed, with its words); a start sweeps once. No webhook and no schedule: the next talk anyone starts or ends cleans up what the last run left. It writes a log line of its own, with the same request id, only when it deleted something or something failed (`voice:sweep:<count>`, with `:failed:<word>` after it).
- `GEMINI_MODEL`, `GEMINI_SCREENING_MODEL` and `GEMINI_FALLBACK_MODEL` have no default in code (the screening falls back to `GEMINI_MODEL` only when its own is empty, and with no fallback model every attempt goes to the first one), and every Gemini request sets `store: false`.
- A secret is a name in `supabase/functions/.env.example` and a value only in `supabase/functions/.env.local` (git ignores it) and in the hosted project. Nothing prints a value.
- The user deploys: login, `secrets set` and `functions deploy` are theirs to run, and the implementer never holds a management token. A change to a function is not live until they deploy it, and each function is deployed on its own (`functions deploy process-entry`, `functions deploy confirm-scripture`, `functions deploy delete-entry`, `functions deploy sync-subscription`, `functions deploy revenuecat-webhook`, `functions deploy export-data`, `functions deploy delete-account`, `functions deploy add-affirmation`, `functions deploy scholar-turn`, `functions deploy scholar-speak`, `functions deploy scholar-voice-start`, `functions deploy scholar-voice-llm`, `functions deploy scholar-voice-end`), and a migration that a function reads is applied before that function is deployed (step 29b: `deleted_devotionals` before `process-entry`, whose limit check reads it: deployed first, every free account's reflection fails with a 500; step 30: `subscription_sync` before `process-entry`, `sync-subscription` and `revenuecat-webhook`, which read and write its two columns; step 31: `exports_bucket` before `export-data`, which writes into it; step 36: `validation_line` before `process-entry`, which writes the column: deployed first, every reflection fails with a 500; 2026-11-09: `more_affirmations` before `process-entry`, whose three inserts carry `position` (deployed first, every reflection fails with a 500), and before `add-affirmation`, which calls `feature_affirmation`; the migration first and the old `process-entry` is fine, because the trigger fills a missing position; step 38: `scholar_conversations` before `scholar-turn` and `scholar-speak`, which read and write its tables, and before the new `export-data` and `delete-account`, which read and delete them: deployed first, every export and every account deletion fails; 2026-11-11: `help_lines` before `process-entry`, which writes `help_line` with every reflection (null for an ordinary one; deployed first, every reflection's save fails with a 500 and waits in the phone's outbox), and before `scholar-turn` and `scholar-speak`, which read and write `scholar_closed_at`; the app reads `help_line` in its column list since the same day, so an app with that code (Metro on a development project, or a store build on production) runs only against a project that has the migration, or the Journal cannot load; step 39: `scholar_voice` before `scholar-voice-start`, `scholar-voice-llm` and `scholar-voice-end`, which read and write its table, and before the new `delete-account`, which counts it (deployed first, every account deletion fails); then the secrets, then the eight agents (`agent_setup.ts`, which writes `ELEVENLABS_AGENTS`), then the functions in the order `scholar-turn`, `scholar-voice-start`, `scholar-voice-llm`, `scholar-voice-end`, `delete-account`; 2026-11-18: `scholar_credits` before `scholar-turn` and `scholar-speak`, which read and spend it (deployed first, every Scholar message, a heavy one included, and every answer read aloud fails with a 500, because the credits are read before the screening), and before `delete-account`, which counts it, then the functions in the order `scholar-turn`, `scholar-speak`, `scholar-voice-start`, `scholar-voice-llm`, `scholar-voice-end`, `delete-account` (`process-entry` uses only the tier of what `confirmPaidPlan` answers, so its deploy can wait for the next one). ### Billing (step 30)

RevenueCat is the source of truth for a person's plan; the server never takes the app's word for a purchase. `_shared/billing/revenuecat.ts` is the only code that talks to RevenueCat (step 31 imports it for the customer delete).

- **One entitlement, `pro`**, a constant (`PRO_ENTITLEMENT_ID` in `_shared/billing/revenuecat.ts` and in `src/constants/app.ts`), never an environment variable. No product id is ever in code: the app uses RevenueCat's current offering (`default`) and its Annual and Monthly packages.
- **`syncSubscription` writes the plan**, and nothing else does: it re-reads the customer (`GET https://api.revenuecat.com/v1/subscribers/{id}` with the V1 secret key; two attempts of 8 seconds, one retry after about a second on 429, a 5xx, a timeout or a dropped connection, never on another 4xx; the answer is checked by hand-written guards, and any 2xx counts, because RevenueCat answers 201 for a customer it has just created) and writes `subscription_tier`, `subscription_expires_at` and `subscription_synced_at` on that user's row only (service role, filtered by the id; no row: nothing is created). `pro` is active while its `expires_date` is null (a lifetime grant) or later than now, or its grace period ends later than now; active in a trial period is `trial`, active otherwise `pro`, not active `free`; an unparsable date counts as absent and is never read as a lifetime grant. Three callers: the webhook, the app (`sync-subscription`), and process-entry's expiry guard. Re-reading makes every event and every retry harmless to repeat, so no events table exists. Failure reasons are words only (`http_401`, `http_404`, `http_429`, `http_5xx`, `timeout`, `network`, `bad_body`, `db:update`).
- **The webhook needs both checks** (Authorization and HMAC), does its work before it answers, and answers 200 only when every sync succeeded (Edge Function Rules).
- **The expiry guard in process-entry**: just before the free limit (after the screening, so a heavy moment never reaches it), a trial or Pro row whose `subscription_expires_at` has passed is re-read from RevenueCat once (one attempt, 6 seconds, `EXPIRY_CHECK`), and its answer decides the limit. RevenueCat unreachable, or billing not set up, leaves the stored plan (`billing: failed:<reason>` or `off`): a paying person is never blocked by an outage. A null end date (rows from before step 30, lifetime and promotional grants) is left as it is.
- **After a purchase or a restore** the app waits for `sync-subscription` (10 seconds, `SYNC_SUBSCRIPTION_TIMEOUT_MS`) and then the profile sync before it answers, so the Paywall's welcome comes once the server knows, and `upgradeWatcher` sends what the free limit held. A failed sync does not fail the purchase: the webhook and the next foreground catch up.
- **Logs**: one word (`billing`), its time (`billingMs`) and, for the webhook, the event's type (`billingEvent`); never a webhook body, a RevenueCat answer, a key or a user id (only the 8-character hash). The log line has 43 fields since step 37.

### Account export and deletion (step 31)

Profile's Export Journal and Delete Account run on the server: `export-data` and `delete-account`, called through `src/api/journalApi.ts` (`exportData` and `deleteAccount`, 155 seconds each, above the functions' own 150) by `src/services/account.ts`. `_shared/account/` holds what both share: `storageFiles.ts` (`listAllFiles`: every file under a person's folder, paging Storage's list by 100 and going into every sub-folder; `removeAll`: removal in batches of 100, and a path that is not there is no error), `userData.ts` (`collectUserData`: the profile and every entry oldest first in pages of 500, each with its affirmations, every query filtered by the person) and `clerk.ts` (`readClerkSecret`, `getClerkUser`, `deleteClerkUser`: Clerk's Backend API, one attempt of 8 seconds each, the only code that talks to it). `_shared/billing/revenuecat.ts` gained `deleteSubscriber` (one attempt; 404 is done) and is still the only code that talks to RevenueCat.

- **The export's contents**: `README.txt` (what is inside, when and in which time zone it was made, every audio file left out by name with its reason, and a line that the file holds private reflections), `journal.json` (`{ exportedAt, schemaVersion: 1, timeZone, profile, entries }`: every column of the profile, and every column of each entry with its affirmations nested under it, except `user_id`, with `audio_path` and `devotional_audio_path` replaced by `recording_file` and `devotional_audio_file`, the file's path inside the ZIP or null), `journal.md` (newest first; a finished reflection whole, an unverified passage as its reference only, an answered prayer's day as the UTC date of `answered_at`; a heavy moment is a reflection like any other and never labelled; one saved before 2026-11-08 and an entry that never finished are only their day and the person's words, with no heading or label) and `audio/recordings/{YYYY-MM-DD}-{entryId}.m4a` and `audio/devotionals/{YYYY-MM-DD}-{entryId}.wav`, the day in the profile's time zone. A recording with no reflection (an upload that never reached process-entry) is not in the export; the deletion removes it. Since step 38 `journal.json` is `schemaVersion` 2 with `conversations` (each Scholar conversation with every column but `user_id`, and its messages, every column but `user_id`, nested under it oldest first), and `journal.md` ends with a "Scholar conversations" section, newest first, each with its title or "A conversation with Scholar", its day and the messages in order (a passage as its reference and text, a prayer ending in "Amen."); a heavy conversation is exported like any other and never labelled, and the README names the section.
- **Size and time**: `EXPORT_MAX_BYTES` is the project's global upload limit less 2 MB: 50,331,648 bytes on the Free plan's 50 MB, which Supabase counts as 52,428,800 bytes (its dashboard source, read 2026-10-30). The texts are budgeted at their largest first; then the person's own recordings, newest first, then the devotional audio, newest first, each only while the ZIP stays under the cap (a file whose size the listing gave is skipped without being downloaded) and the request is under 120 seconds (80% of 150). What is left out is listed in the README and the answer says `partial: true`. The ZIP is built once with fflate's `zipSync` (text at level 6, audio stored) and checked against the cap before it is stored.
- **File times**: every file in the ZIP is stamped with the export time on the profile's clock (`zipTime`), because a ZIP time has no zone and readers show it as written.
- **One export per person, reused for 10 minutes**: a request within 10 minutes of the newest export answers a fresh link to that same ZIP (`reused: true`, `partial` from its name) and builds nothing; after that the older exports are removed and a new one is built. No rate limit. The ZIP lives at `exports/{userId}/{exportId}.zip` (`-partial.zip` when audio was left out) until the next export or the account's deletion; the link lives one hour (`LINK_SECONDS`) and downloads as `gracehush-journal.zip`.
- **The deletion's order**: every secret is checked and Clerk is asked whether the caller exists before anything is deleted (the token has just proved it, so a 404 means a key of another Clerk instance: `500 INTERNAL`, `config:CLERK_SECRET_KEY`, nothing deleted). Then every file of the person in `journal_media` and `exports`; the profile row (its entries, affirmations, records of deleted devotionals and, since step 38, its Scholar conversations, messages and usage go with it, `on delete cascade`), then a count per table and a delete of anything left (`:cascade_missed`); the RevenueCat customer (404 is done); Sign in with Apple, best effort (below); the Clerk user (404 is done; last, so the token keeps working for a retry); and a final pass over storage and the database that removes anything written during the run (`:late_data`), best effort (`:final_pass_failed` is logged, never a failure). A step before the final pass that fails is `500 DELETE_INCOMPLETE`: what was done stays done, and a retry continues.
- **The app's side**: before it asks, the app stops its own background work, so nothing it does can make the account's data again: the sync engine, the plan watch and the profile sync (`pauseProfileSync(userId)`: no sync for that account makes its profile row, not even one a foreground starts). A failure starts them again (`resumeProfileSync`, the engine if it was running, `startPlanWatch`) and clears nothing. A success, or `UNAUTHORIZED` (the account or its session is already gone), runs `signOutCleanup()` and `forgetUser(userId)`, and Profile signs out of Clerk, ignoring the error clerk-js 6.39.1 throws once the user is gone (it clears the session on the phone before it asks Clerk). The mock data source keeps the step 15 mocks (with "Fail next save (dev)"); a release build never reaches them.
- **Sign in with Apple** (step 35) is not revoked by deleting the Clerk user, and Clerk keeps no Apple token, so the phone asks Apple for a fresh authorization code at deletion (`services/appleReauth.ts`: `AppleAuthentication.signInAsync` with no scopes) and `delete-account` exchanges it at `/auth/token` and revokes the refresh token at `/auth/revoke`, with a client secret it signs per request (ES256, `_shared/account/apple.ts`). It runs only for an account with an Apple external account, on iOS, in a real build, on the real data. A cancel on Apple's sheet keeps the dialog open and deletes nothing. Any other failure, or a different Apple Account on the phone, goes on with no code, because Apple says the deletion must still be fulfilled, and a code is never sent for another Apple Account. On the server it runs after RevenueCat and before Clerk, one attempt of 8 seconds per call, and it never fails or stops the deletion; its one log word is `accountApple`. A 200 from `/auth/revoke` proves nothing (it answers 200 even for a made-up token), so the exchange is the only server-side evidence and iOS Settings is the real proof. The code goes to the function once and is never stored or logged. Not built: listening for Apple's `credentialRevokedNotification` (a release-review item).
- **Known limits**: another signed-in device can keep writing for up to a minute after the deletion began (a Clerk session token lives 60 seconds and the functions verify it without asking Clerk); the final pass catches what arrives before it ends. A retry sent within that minute after a deletion that finished on the server but whose answer was lost answers `config:CLERK_SECRET_KEY` (Clerk no longer knows the user); after the minute the phone cannot get a token, the gateway answers `UNAUTHORIZED` and the app signs out. A ZIP whose texts alone outgrow the cap fails as `zip_over_cap`.
