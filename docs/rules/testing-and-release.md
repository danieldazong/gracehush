## Linting and Validation

Run:

```bash
npm run lint
npm run typecheck
```

Check the real exit codes and read the full output. Never pipe these commands through `tail` or `head`, which hides failures. Lint warnings count: fix the cause instead of disabling the rule.

Typecheck and lint cannot catch Metro, NativeWind, or import-resolution problems, so also bundle the app:

```bash
npx expo export --platform android --platform ios --output-dir <a temp folder outside the repo>
```

### Guided phone walk-through (after every step)

Decided with the user on 2026-10-26; on 2026-10-27 they gave it again as a general protocol, which this section sets up for this project (Instructional Memory). After a step is implemented, the agent does not stop at tests and type checks: it offers a guided, human-in-the-loop test on the real device. The user does the physical actions. The agent checks every result itself and reports PASS or FAIL with evidence. Every step prompt carries its checks as "Part B: the phone walk-through", B0, B1 and so on (`prompts/TEMPLATE.md` says how a prompt writes them).

**Project setup**

- **Target:** the Gracehush development build on the user's iPhone, connected to the dev server on this PC (`npx expo start -c --dev-client`, port 8081; the target's `appId` is `com.gracehush.app`). Expo Go is `npx expo start --go`, for a step that says so. The Android emulator (`gracehush_test`, driven with `adb`) only with the user's yes: it holds their own signed-in account, and its Expo Go 57 cannot open this SDK 58 project until the 58 APK is installed (see "Verifying on this machine").
- **How the agent observes, read-only:** the dev server's Hermes inspector (point 4), through which it reads the app's stores and calls the app's own read-only functions and queries.
- **What the agent cannot reach:** the hosted Supabase project (there is no database password and no management token: the user runs the SQL the agent writes in the SQL editor, or reads a row in the Table Editor); the Supabase, Clerk and Google dashboards; the app while it is in the background or the phone is locked (while a devotional plays, the recorder keeps logging and is read on the way back); and the iPhone itself (there is no Mac, so nothing on this PC can tap it).
- **Restart needed after a change:** `npx expo start -c --dev-client`, then force-quit and reopen the app, when a step adds files or assets, or changes `app.json`, `metro.config.js`, `global.css` or `package.json` (a hot reload carries none of these). A changed Edge Function is live only after the user deploys it, and a migration only after the user runs it in the SQL editor.
- **Where results are recorded:** the step's entry in `docs/build-log.md` (point 8), never in this file.

1. **Ask first.** When the step is implemented and its automated checks pass (Part A of the step's Verify: typecheck, lint, the Node and Deno checks and the bundle exports), end the report with one line: "Automated checks pass. Shall I start the guided walk-through now (B0 to Bn)? Keep Gracehush open on the iPhone, in front and connected to the dev server." Then wait. If the step has nothing to check by hand, say so in the report instead. Never start the walk-through, and never ask for results one check at a time, before the user says yes.
2. **Roles.** The user is the hands: taps, typing, speaking, Airplane mode, dashboard changes, and running any SQL or command the agent writes. The agent is the eyes and the judge: after every action it checks the result itself and reports what it read. It never takes the user's word as the only evidence when it can read the result itself, and it never guesses.
3. **How the checks are written.** In the step prompt, as `prompts/TEMPLATE.md` ("Phone walk-through") says: what needs a restart, which account, plan and data the run needs, what it costs and that the app stays open, said once before B0; B0 is the starting state; and each check has a **Do**, an **Expect** and a **Read** line.
4. **How the agent observes.** Read-only, always. `GET http://127.0.0.1:8081/json/list` lists the running app as a target, and a Node script with the project's `ws` package (Node's own WebSocket fails on the proxy) opens its `webSocketDebuggerUrl` with an `Origin` equal to the dev server's own origin (the host of the manifest's `launchAsset.url`; with no Origin the proxy answers 401 and prints a red line in the user's Metro terminal; ask the manifest from `http://127.0.0.1:8081` and use the host it names: on 2026-10-28 `http://127.0.0.1:8081` worked and the LAN address answered 401) and sends `Runtime.evaluate` with `returnByValue`. A probe reads store state, counts and statuses, and can call the app's own functions through `__r(<module id>)` (ids from a saved dev bundle of the same options: `__r.getModules()` answers an empty map on SDK 58, so the bundle is the only way; the ids hold until the dev server is restarted). `awaitPromise` does not wait on Hermes: put the result in a global (`globalThis.__probe = "pending"; (async () => …)().then((r) => (globalThis.__probe = r))`) and read the global a few seconds later. `Runtime.enable` replays the app's own console lines since its JavaScript last started. Whether a fixed string of the app's own copy is drawn right now (a banner, a row that must not be there) can be read too: walk the fibers from `__REACT_DEVTOOLS_GLOBAL_HOOK__.getFiberRoots(rendererId)` (child, then sibling) and compare `memoizedProps.children` with the string, printing booleans and counts only (2026-10-29, step 29: the walk saw the whole crisis view, the parts below the fold included). It works only against the dev server (a development build), not a release build. With the user's yes the agent also drives the app: a control's own handler found in the same fibers (`onPress`, `onChangeText`, `onConfirm`), and a small helper armed in the running app that waits for a condition (a tapped tab, the phone going offline) before it goes on, so the user's part is the physical action. It saves each read of its recorder to a file first, because a read empties it, and it reads before the user leaves the app, because iOS can end the app's JavaScript after minutes in the background. Layout is measured rather than asked for: `nativeFabricUIManager.measureInWindow(fiber.stateNode.node, callback)` gives a host view's bounds in points, and the user asked for this (2026-11-03, "automate and check it yourself"), so a screenshot is for what only a picture shows. A whole sequence can be one script armed in the app that waits for one tap and then moves through the screens by itself. Every request to the app needs a time limit, because none is answered while its JavaScript is paused, and two instances of a component can be mounted, so read the visible one. Permanent deletions are the user's to press. Probe scripts live outside the repo (the session's scratchpad), never in the project's source. A database fact is read through the app's own query, or with a SQL statement the agent writes and the user runs in the SQL editor and sends back.
5. **What a probe cannot read:** the sound, how a screen looks, animations, haptics, what the lock screen or a notification shows, what VoiceOver says, and the OS permission prompts. For these, ask for a screenshot or a one-word answer. With no answer, the check is "not verified", never PASS.
6. **Keep the target reachable.** iOS pauses the app's JavaScript when it is minimized or the phone is locked, and the target list comes back empty (`[]`): tell the user to bring the app to the front and wait. Never report a result you could not read. After a long time in the background a development build can stay on screen with no link at all, and a force-quit and reopen brings it back; right after that the list can show the development launcher under the same name, whose runtime has no `__r`, so a probe answers "Property '__r' doesn't exist": read `typeof __r` until it is a function before driving anything (2026-11-04). When the list stays empty with Expo Go back in front (it did on 2026-10-28 each time another app, such as the Clock app, had come to the front), a reload from the developer menu does not bring it back; a force-quit and reopen of Expo Go does, and it ends the app's in-memory state, a probe's listener included, so read what a check needs before the user leaves the app.
7. **The loop, for each check.** (1) Give ONE action and stop. (2) Wait for the user's "done" (or a screenshot). (3) Check: run the probe, query or request, and compare the result with the check's Expect line. (4) Report PASS or FAIL with the evidence you read (the value, count, status or screenshot detail). (5) On a FAIL, stop and find the cause before the next check. If a fix is needed, say what it is, get the user's yes, fix it, and run the failed check again.
8. **Record the results.** At the end, replace the step's "phone walk-through: not run yet" line in its log entry in `docs/build-log.md` with one line per check (what the user did, what was read, PASS, FAIL or not verified), and list separately what could not be checked on this target and why (for example an App Store purchase, which waits for section H of step 35).
9. **Rules.** Probes never print secrets or private content: no token, key, password, full user id or email, and nothing the person wrote and nothing the app made from it (a transcript, a verse, a devotional); counts, statuses, short ids and times only. Never sign in, write, delete, purchase or send anything on the user's behalf without asking first (a test account included). Do not edit source files during the run: Fast Refresh reloads the app and loses its in-memory state. Never point the emulator, which holds the user's real account, at the real project without their explicit yes. Do not ask the user to test something that cannot work on this target (Siri on their iPhone, an App Store purchase before Apple has accepted the tax form): mark it "not verified" and say where it can be tested.
