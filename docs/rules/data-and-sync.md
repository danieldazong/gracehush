# Data, offline cache, sync and Realtime

> Part of the GraceHush rules, moved out of `AGENTS.md` word for word on 2026-11-23. `AGENTS.md` is the short core that every session loads, and its "Rules index" says which file holds which section. The sections below keep their original `##` headings, so a reference such as "AGENTS.md, Crisis Safety Rules" finds them. A rule that changes is changed here, in its section, in a few lines; a step's history goes to `docs/build-log.md`. This file can be long: search it (`git grep -n "<words>" docs/rules/data-and-sync.md`) and read only the part you need.

## Local Cache & Offline Rules

- Every new entry is saved locally **first** (status `pending`), then synced.
- Sync queue states: `pending` → `uploading` → `processing` → `ready` | `failed`.
- Show the Offline banner and "Waiting to sync" chips from the Journal design while offline.
- Retry failed syncs with backoff when connectivity returns. Never silently drop an entry.
- The local database holds sensitive text, so the **words** in it are encrypted (decided in the step 24 review, 2026-10-25): AES-256-GCM through expo-crypto's native AES, one random key per signed-in user in SecureStore (`gracehush.dbkey.{hash}`, on this device only, while it is unlocked), each value sealed on its own (`v1.` plus base64 of nonce, ciphertext and tag). That is the written entry in the outbox and the entries and affirmations in the read cache; ids, statuses, counts and times are not encrypted. SQLCipher was not chosen: expo-sqlite's own docs say it is unavailable in Expo Go, it needs a native build that does not exist, and its key must be applied to every connection. The database is one file per user, `gracehush-{first 16 hex of SHA-256(userId)}.db`. Sign-out and account deletion delete the file, its key and every recording. A key that is gone while the file is still there means its words can never be read again, so the file is deleted and made new (`db_key_reset` is all that is logged). Text is stored only there, never in AsyncStorage.
- A reflection is saved in the outbox **before** anything is sent (step 24), and the sync engine prepares them one at a time, oldest first, only while the app is open and the phone can send. It never runs in the background, it never retries what only the person can fix (`needs_action`), it holds what the free limit stopped until the plan is paid or the week resets (`limit_reached`), and it asks again for a refused session once per visit (`paused_auth`). Backoff is 5 s, 15 s, 60 s, 5 min, 15 min, then 1 h, with 20% jitter, and at least 60 s after `RATE_LIMITED` and 30 s after `ALREADY_PROCESSING`. A pending reflection is listed on Journal as an entry-shaped card that never shows its words.
- The server is the source of truth once an entry is `ready`. Since step 25 the Journal and Reflection read it from Supabase through this cache (see Journal Data Rules below).
- Deleting a reflection (step 29b) is the one write that needs a connection: the server confirms it before the phone forgets anything (the cached entry, its affirmations, the prayer change that waits for it), and it is never queued. Removing a prayer from Prayers is queued like any prayer change.
- A prayer change made on this phone (step 29) is written to the cached entry at once and kept in the `mutations` table (schema version 3) until the sync engine has sent it: one row per entry, every change merged into one patch (a later key wins), the patch encrypted like the other words (a gratitude note is the person's), sent before the outbox in each run. See Prayer Rules.

## Journal Data Rules (step 25)

Built in step 25 (2026-10-25); the code and its checks are in `prompts/25-journal-reflection-data.md` and `supabase/tests/journal-data/`.

- **One switch.** `getDataSource()` (`src/data/mock/scenario.ts`) is `"supabase"` or `"mock"`. A release build is always `"supabase"`; a development build follows the dev panel and falls back to `"mock"` when `.env.local` has no Supabase address. With `"mock"` the screens run on the step 06 data and the dev store's outcomes and plans, nothing reaches the server, and the sync engine writes nothing to the read cache. Step 25 renamed `profileSource` and `getProfileSource` to `dataSource` and `getDataSource`, which decide the profile, the entries, the affirmations, the usage and the processing of a reflection.
- **Screens read entries and affirmations only through `journalRepository.ts`.** Its real source is `data/entriesLive.ts` (cache first, then the network, everything read written to the cache) over `data/entriesRemote.ts`, the only code that queries `journal_entries` and `daily_affirmations`. Since step 29 the prayers go through them too (Prayer Rules).
- **The Word Deck reads the cache as well (2026-11-17).** The deck's pool is the phone's newest 40 cached entries (`WORD_DECK_LOOKBACK`), so a reflection older than the newest 40 entries is not in it. The affirmations of a pool reflection that the phone has none cached for are fetched in one request when Journal loads, online only, and written to the cache by id (`selectAffirmationsForEntries`, the explicit columns and the user filter like every other read); with no answer the reflection is left out until the next load. Nothing about the deck is read from the server but those affirmations: the calendar is the phone's own.
- **The Today deck of words reads behind the list (2026-11-20).** Its cards are the reflections the Journal has loaded, so it reaches back as far as the list does and asks for the next page near its end. Each card's words are its reflection's affirmations: the phone's own first (`readCachedWords`, by entry id, each list in position order, an entry with none left out), then, behind each page from the server, one request for those of the page's finished reflections the phone holds no affirmations for (`hydrateWords`, which shares `fetchMissingAffirmations` with the Word Deck's `hydrateWordPool`: `selectAffirmationsForEntries`, the explicit columns and the user filter, written to the cache by id), and no request when the phone holds them all. A list already on screen is never replaced by a later read of the phone, so a heart tapped while words are on their way is not undone by an older read; the heart flips its card at once, a Realtime event re-reads its own entry's words, and a pull-to-refresh reads every list again. On the mock data the words are the mock rows and nothing reaches the server. Known limit: a change to an earlier reflection's words made on another phone while Today is covered (a heart, say) reaches the cache through Realtime and shows on its card after a pull-to-refresh, not by itself.
- **Cache first.** A screen shows what the phone has at once (the read cache: one page plus 20 spare rows, because every row read is decrypted), then the first page from the server replaces it. A failed refresh keeps what is on screen; with nothing on screen it is the error state. Coming back to the app keeps the older pages already on screen; pull-to-refresh starts again from the first page.
- **Explicit columns, always.** `data/columns.ts` lists them and a check compares the lists with the generated types: never `select("*")`, never `audio_path` (where the raw recording is stored), never an embedding, and `user_id` only as a filter. Every query filters by the signed-in user's id as well as row level security.
- **Pages.** 30 entries, newest first, by cursor on `created_at` (the last row's text, as PostgREST wrote it) with one row more than the page, to know whether another follows. Every page asks for the count (`count=exact`) and only the first page's is used (a later page would count only what is older); only the first page trims the cache: to the newest 200, and since step 29 every prayer besides them. A filter works on the entries loaded so far.
- **What the Journal lists.** Finished entries (a heavy moment included) and entries still `processing` that were touched in the last 10 minutes. A failed entry is not listed: the phone that made it shows its outbox card, and a refused or deleted reflection is no reflection. A `processing` entry that nothing has touched for 10 minutes belongs to a request that died and is not listed. A reflection waiting on this phone is shown from the outbox and hides its server copy (same client entry id).
- **Reflection.** The cached copy first, then the server's. An entry the server calls `processing` (made on another phone, or this phone stopped waiting), and since 2026-11-09 a finished reflection whose audio is still being made behind the answer (`isAudioPending`: no audio path, no `TTS_FAILED`, changed within AUDIO_PENDING_MS), is read again every 5 seconds while the screen is in front, for at most 2 minutes, only while Realtime is not live (Realtime Rules); the hook says `audioPending` for the player card, and reads the entry again from the phone when the window passes. An entry that is only in this phone's outbox is never read from the server, and nobody is asked for its affirmations. Opened by the client entry id of such an entry (New Entry's handoff, 2026-11-10), the hook follows the sync engine's `finished` and `settled` events for that id and reads by the server's id from the finish on; `getEntry` finds a reflection that finished meanwhile in the cache by its client entry id, before it asks the server. A passage kept as a reference is asked for again (`confirm-scripture`): at most once a minute per entry, never while the phone is known to be offline, never for the mock data, an unfinished entry or one with no reflection (a heavy moment saved before 2026-11-08), and the answer (verified, still unverified, or none) is shown and cached; a failure changes nothing and shows nothing.
- **Edge Functions are called only through `src/api/journalApi.ts`** (`processEntry`, `confirmScripture` and, since step 29b, `deleteEntry`; the developer check is the one exception). The user id never travels in a body: the Clerk session token the Supabase client already sends identifies the caller. A call answers `{ ok: true, data }` or `{ ok: false, status, code, body }`, never throws, and the shape of an answer is checked by hand-written guards. Timeouts: `process-entry` 155 s (the function ends by about 145, the platform stops it at 150, the sync engine's own ceiling is 200), `confirm-scripture` 15 s, `delete-entry` 30 s (a few Storage and database calls from a region far from the database; a timed-out request may have succeeded, and the retry answers `NOT_FOUND`, which counts as deleted). A code is the function's own, or `NETWORK` (no answer, status 0), `UNAUTHORIZED` (no session, 401 or 403), `RATE_LIMITED` (429), `INTERNAL` (5xx) or `UNKNOWN` from the status. Nothing is logged but a name, a status, a code and a time.
- **Server times have one form.** PostgREST writes a timestamptz as `2026-10-25T11:59:00.123456+00:00`; the app keeps it as `2026-10-25T11:59:00.123Z` (`utils/timestamp.ts`: three fractional digits and a `Z`, the milliseconds cut, not rounded) at the two places a time enters, `entriesRemote.ts` (the rows) and `entryProcessor.ts` (the entry the function answers with). The Journal's page cursor is the one text kept exactly as the server wrote it, because PostgREST compares microseconds. `toJournalEntry` is untouched, so it still equals what the function's `response.ts` makes of a row.
- **A recording is uploaded once** (`outbox.uploaded`, schema version 2) and then `process-entry` names its path. A reflection the server already has is found by its client entry id, so sending it again never makes a second one.
- **The free limit belongs to the server.** Profile's "n of 3 used" is a number to show: the devotionals this phone has this week (finished, not a heavy moment, with a devotional), counted from the read cache in the profile's time zone and capped at the limit. `src/utils/week.ts` is a copy of the server's `weekWindow`, and the checks keep the two equal. Only a 402 opens the Paywall. The 402's `entryId` and `resetsAt` are kept on the held item.
- **A plan that turns paid sends what the limit held.** `services/upgradeWatcher.ts` watches the plan the profile sync brings (a purchase on this or another phone, the webhook of step 30, or a change by the server) and calls `resumeAfterUpgrade()`; a mock purchase calls it on its own.
- **The heart is saved** on the server (`daily_affirmations.is_favorite`, the one column the app may write there) and in the cache. It shows at once and goes back with a calm line when the save fails.
- **The "days of reflection" chip** (step 33) is the server's run of days, `reflection_streak_days(tz)` in the profile's time zone (`getReflectionStreak` in the repository: the answer is kept in memory for the account and the day, and a failed call later that day answers it). Journal asks for it after its first page and when a reflection finishes; until it answers, offline, with the mock data and on an error, the chip counts what the phone holds (`getReflectionDays`). Since 2026-11-16 the number is no longer drawn: it is the week strip's spoken sentence (`streakDays`), and the strip draws the last seven days.
- **Never** log a transcript, a verse, a body, a token, a path or an id; never log anything about a heavy moment; never open the Paywall from a number.

## Realtime Rules (step 33)

Built in step 33 (2026-10-31); the code is `src/services/realtime.ts`, `src/services/realtimeHandlers.ts` and `src/store/realtimeStore.ts`, the migration is `20261031120000_realtime_broadcast.sql`, and the checks are `supabase/tests/realtime/` and checks 57 to 64 of `rls_selftest.sql`.

- **Broadcast from the database, not Postgres Changes.** Postgres Changes would send whole rows (the transcript, the verse, a gratitude note). Triggers on `journal_entries` (insert, update, delete) and `daily_affirmations` (insert, update) send a short message to the owner's private topic `user:{userId}` through `realtime.send`: `entry_changed` with `{ id, op, status, updated_at }` and `affirmations_changed` with `{ id, entry_id }` (the affirmation's id is the one `realtime.send` would add anyway). Nothing a person wrote or the app made from it is ever in a message, and the crisis flag is not either.
- **A message never fails a write.** Each trigger catches a failed send (no message table for the day yet, Realtime off) and raises a warning that names no value. Supabase makes the day's message table when a client connects, so a message sent before the day's first connection is lost, which the screens' own loads cover.
- **Only the owner receives, and the phone never sends.** One `select` policy on `realtime.messages` for `authenticated`: the topic is `'user:' || requesting_user_id()` and the extension is `broadcast`. No insert, update or delete policy. "Allow public access to channels" is off on the project (Realtime, Settings), so only private, policy-checked channels exist. `realtime.messages` is Supabase's table: its policies are the only thing the app's migrations touch there.
- **When it runs.** Only while someone is signed in, the data source is the real one, the user's database is open, the app is in front and the phone can send (the sync engine's `selectCanSend`), and not while "Force polling (dev)" is on. It stops as soon as one of these ends (iOS would close the socket in the background anyway) and starts again when all hold. The auth bridge starts it at sign-in; `signOutCleanup()` stops it first, before the database and the token go, and `deleteAccount()` stops it before its request and starts it again when the deletion fails.
- **The token.** The app's one client outlives a sign-out, so `client.realtime.setAuth()` (no argument: it asks Clerk through the `accessToken` callback) is awaited right before every subscribe. After the join the app checks it every 5 s while the channel is live (`REALTIME_TOKEN_CHECK_MS`: started on `SUBSCRIBED`, stopped by every stop and failure), because Realtime's own refresh at its heartbeat (25 s) can come after the token has expired: Clerk mints the next token only 17 s before the old one runs out, in a background fetch that can fail or come late (found in the walk-through, 2026-10-31). A check renews a cached token that has 15 s or fewer left (`REALTIME_TOKEN_RENEW_S`; `renewSessionTokenIfExpiring` in `supabaseClient.ts` calls `getToken({ skipCache: true })`, never with a template), then calls `setAuth()`, which reads Clerk's cached token; Realtime sends it only when it changed.
- **A dropped channel.** `CHANNEL_ERROR`, `TIMED_OUT` and a `CLOSED` it did not ask for remove the channel and try again with the sync engine's backoff (`retryDelayMs`: 5 s, 15 s, 60 s, 5 min, 15 min, then 1 h, with 20% jitter) while the app is in front; the status is `offline` with a one-word reason (`unauthorized`, `private_only`, `timed_out`, `closed`, `channel_error`) while it waits, and `SUBSCRIBED` resets the backoff. When a channel that was live comes back after dropping while the app stayed in front (a failure, the phone offline, Force polling), Realtime emits `resync` and counts a reconnect, and Journal, Reflection and Prayers load again from the server; not on the first join of a session and not after a return to the front, when the screens reload by themselves. A generation counter drops anything that lands after a stop or a failure: a read on its way writes nothing (`fetchEntry` and `fetchAffirmations` take a `keep` check) and tells nobody.
- **What a message does** (`realtimeHandlers.ts`). An INSERT or UPDATE is read once per entry, 300 ms after the last message about it (`REALTIME_COALESCE_MS`), one read at a time; a message that arrives during a read schedules one more. It is skipped when the cached entry's `updatedAt` is the same or newer (compared as times in the step 25 canonical form: the app's own changes come back this way), and when its outbox item is being sent (the engine writes the answer itself). The read is `fetchEntry` (the network, this phone's waiting prayer changes on top, written to the cache); an entry the server no longer has is handled as a delete. A reflection that has just finished reads its affirmations before the notifications are planned again (`requestAffirmationReschedule()`; a heavy moment's are read like any other's since 2026-11-08), and a **queued** outbox item for it (this phone gave up waiting) is made due now (`makeDue`) and the engine woken (`syncNow("realtime")`), so the waiting card turns into the reflection. A DELETE forgets an entry the phone holds (the cache or the loaded player: `forgetEntry`, then `forgetOnThisPhone`) and does nothing otherwise, so this phone's own delete coming back is harmless. `affirmations_changed` reads the entry's affirmations once per burst and plans the notifications again. Each reaction ends with an event the screens follow: `entry` (with the id and the operation), `affirmations` or `resync`.
- **The screens.** Reflection reads its entry and its affirmations again from the phone on an event for them, shows "not found" on a Realtime delete (a delete made on the screen itself leaves the screen, so the sync engine's own `deleted` event is not followed there), and polls a server that is still preparing it every 5 s only while Realtime is not live (`isRealtimeLive()`, false while Force polling is on). Journal merges a changed entry into its list: a listed entry takes its place or joins the loaded range (one more in the known total), an entry no longer listed (a failed one) leaves (one fewer), and the newest reflection's affirmations are read again from the phone. Prayers reads its list again from the phone. All three load again from the server on `resync`.
- **The run of reflection days.** `reflection_streak_days(tz)` counts the caller's own consecutive local days in `tz`, ending today or yesterday, each with a ready entry that has its devotional (since 2026-11-08 a heavy moment counts, and one saved before then with only its words does not; the same rule as `getReflectionDays`), `security invoker`, and an unknown zone raises `22023`; Journal Data Rules says how the chip uses it.
- **Logs**, development only: `[realtime] <status>` (with the one-word reason) and `[realtime] realtime_bad_payload`. Never a payload, a topic, a token or an id. A payload that does not have the contract's shape is ignored (the guards read only the contract's keys).
- **Not used:** Broadcast Replay (the screens reload on focus, on a return to the front and on `resync`), presence, Realtime in the background, and messages about the profile or the plan (the profile sync of steps 17 and 30 keeps them).

## Scholar Data Rules (step 38)

Built in step 38's Part Two; the code is `src/data/scholarRepository.ts` over `src/data/scholarRemote.ts`, `src/hooks/useConversation.ts`, `useScholarHome.ts` and `useScholarHistory.ts` and `src/utils/scholarRows.ts` and `scholarHistory.ts`, and the checks are `supabase/tests/scholar/`.

- **Memory only on the phone.** Conversations are read from the server when they open and kept in the screen's memory: no SQLite cache, no outbox and no Realtime (a conversation is online by nature). Only the turn in flight and the recordings already uploaded are kept for the session, so a screen opened again during a turn finds it; sign-out forgets both (`forgetScholarSession`).
- **One gateway.** `scholar-turn` and `scholar-speak` are called only through `src/api/journalApi.ts` (`scholarTurn` 45 s, 60 s for a spoken message; `scholarSpeak` 20 s), in the database's region (`x-region: us-east-1`), with the phone's region in the body (`deviceRegionCode()`, never when it cannot be read), and, since 2026-11-19, `scholarSpeak` with the chosen voice's key while the account has allowed ElevenLabs (`listenVoice()`; never a voice id). The answers' times are kept in the app's one form (`normalizeTimestamp`), as every server time.
- **Explicit columns.** `CONVERSATION_COLUMNS`, `SCHOLAR_MESSAGE_COLUMNS` and, since 2026-11-18, `SCHOLAR_CREDITS_COLUMNS` (`data/columns.ts`), every query filtered by the user's id, never `claimed_at`; the app's one write is deleting a conversation (its messages go with it), and it only reads its credits.
- **One turn at a time.** A message is drawn at once (its time just after the newest message on the screen, so a phone whose clock is behind still puts it last), the answer replaces it when it comes, and nothing else is sent meanwhile. A failure keeps the message with "Try again", which sends the same id (the server answers a message once and replays an answer it has). A message the server is still answering (under a minute old) is read again every 3 seconds; an older one offers "Try again".
- **The server's conversation id is the one kept** (one conversation per reflection per person: the server may answer with the reflection's existing one).
- **A welcome (scholar-v3, 2026-11-16)** is read from the answer's saved content (`toScholarMessage`, never in a heavy conversation) or from the function's answer, where a missing field reads as false (`withCanonicalTimes`), so the app works with a function from before scholar-v3, and an older app ignores the new field. Only the newest answer's chips follow it.
- **Online only.** Nothing is sent while the phone is known to be offline ("Scholar needs a connection."), and a spoken take is kept for later.
- **The conversation list is paged and searched on the server (2026-11-16).** `listConversations({ limit, cursor?, query? })` answers a page and the next cursor: newest first by `last_message_at`, one row more than the page to know whether another follows, the cursor being the last row's time exactly as the server wrote it (microseconds and all: cutting it to milliseconds would skip a row), and `lt` on it for the next page. A title search is `ILIKE` (`likePattern`: the typed words between wildcards, `%`, `_` and `\` escaped, at most 60 characters, nothing for blank words), so it covers every conversation, no migration and no new index (the user filter narrows a search to one person's conversations; a trigram index on the title is the answer if that stops being enough). The tab asks for the latest three (`SCHOLAR_HOME_RECENTS`, plus one to know about "See all"), the Conversations screen for 30 at a time (`SCHOLAR_HISTORY_PAGE`). Nothing is cached: coming back to the screen merges a fresh first page into the loaded pages (`mergeFirstPage`). The mock data pages and searches the same way.
- **Scholar's plan and credits (2026-11-18).** The server decides, after the safety screening, whether a message is answered (Edge Function Rules, `scholar-turn`); the app uses RevenueCat's plan (`useEntitlement`) only to answer a tap on Listen or Talk at once. A message outside the plan is kept with Try again, which sends it again under the same id once the plan includes Scholar: a free account is offered the plans, and a trial is told the day its plan begins (`opensAt`, from the server's `resetsAt`, or from RevenueCat's `trialEndsAt` once RevenueCat has answered). A Pro account's credits are read once when a conversation opens (`readScholarCredits`, only for an account RevenueCat calls Pro) and then come from each answer's `usage`; with 20% or less left a line says so, and with none left the notice says when they renew, its countdown moved every 30 seconds; neither the line nor the countdown is a live region, and neither shows in a heavy conversation. The composer is never disabled by the plan or the credits.
- **Never** a limit number in the app (the server's `usage` and its 402 decide; `SCHOLAR_CREDITS_LOW_PERCENT`, 20, is a threshold for the display and not a limit), a limit that disables the composer, chips or an event in a heavy conversation, or a log line with a word, an id or a token.
- **Live talks (step 39).** `scholar-voice-start` and `scholar-voice-end` are called only through `src/api/journalApi.ts` (`scholarVoiceStart` 15 s, `scholarVoiceEnd` 10 s), in the database's region; the start carries the conversation, the voice key, the reflection when there is one and the phone's region, and nothing else (never a voice id or a user id). A talk's turns are saved by the server as the conversation's messages (the person's words as spoken messages, Scholar's answers as written ones), so the Conversation screen shows them by reading the conversation again when the talk ends (`refreshAfterTalk`, in the conversation the server answered with), and a turn that failed or was released at the cap shows as a failed spoken message whose Try again sends it under the same id, answered from its saved words. The month's talk time is the server's: the start's `limits` and the end's answer; the app counts only the visible countdown. Nothing of a talk is kept on the phone, and sign-out ends a live talk first (`endLiveTalk`).

## Prayer Rules (step 29)

Built in step 29 (2026-10-28); the checks are `supabase/tests/prayers/`.

- **Tracked** is `is_active_prayer`. **Answered** is `is_answered` with `answered_at` (both or neither: the table's `answered_fields_match` rule). The Active tab is the tracked prayers that are not answered; the Answered tab is the answered ones. Turning Mark as Prayer Request off also clears the answer and the note; Move back to Active keeps the prayer tracked.
- **Remove from Prayers versus Delete reflection (step 29b).** Remove from Prayers is `setPrayerTracked(false)` (the same patch as the toggle): it clears `is_active_prayer`, `is_answered`, `answered_at` and `answered_notes` and keeps the reflection, so it is queued like any prayer change and works offline. Delete reflection… deletes the reflection for good (Backend / Edge Function Rules, `delete-entry`), always asks first and works only with a connection. A heavy moment may be a prayer since 2026-11-08 (never by the server: its person tracks it), and its menu is every prayer's.
- **An entry that is not finished is never a prayer**, whatever the flags say (the mapper and the writes say so). Since 2026-11-08 a heavy moment may be one: the server never makes it one, its person may track it from Reflection, and the table's `crisis_not_prayer` rule is gone. No prayer event is sent about it (Analytics Rules).
- **The answered day is a calendar day**: stored as 12:00 UTC on it (`answeredDateToTimestamp`) and read back as the stamp's UTC date, so a phone that moves to Pacific/Kiritimati or Pacific/Honolulu shows the same day. A valid day is between the entry's local creation day and today, both included.
- **The summary** a prayer card shows is the model's (`prayer_summary`), else the reflection's title (`toListedPrayer`), never the transcript. The title is the model's, else "Prayer from {date}". The mapper stays equal to the Edge Function's (`response.ts`), so the fallback is applied where Prayers lists prayers, not in `toPrayer`; `Prayer` gains no field, because it is part of the process-entry contract.
- **The app writes only** `is_active_prayer`, `is_answered`, `answered_at` and `answered_notes` (`PRAYER_PATCH_COLUMNS`; `prayer_category` is granted and never written; `prayer_summary` and `prayer_title` are the server's). A note is trimmed, an empty one is none, and it is at most 1,000 characters.
- **Offline first.** A change is written to the cached entry at once and kept in the change queue (`db/mutations.ts`, schema version 3): one row per entry, every change to it merged into one patch, a later key winning, so marked, edited and moved back offline is one update with the final values. The patch is encrypted. The sync engine sends due changes before the outbox, one at a time, with the step 24 backoff; a row that had a change merged into it while it was on its way is kept and goes next. Every server read written to the cache (Prayers, a Journal page, a reflection) keeps the waiting changes on top, so a change never flickers back.
- **Failures** (`classifyPrayerFailure`, pure): no answer, a timeout, 429 and a 5xx are retried; a refused session (401, a PGRST30x code, or no session) pauses every change until the app starts or comes to the front; a refusal by the database (42501, 23514, 22P02, 22001, or any other 4xx) is dropped, never retried: the change leaves the queue, the entry is read again from the server, and Prayers and Reflection say "We couldn’t save that change." until the next refresh or tab change.
- **Last change wins per field.** Two phones that change the same prayer before either has synced end with the later one's values field by field. Realtime (step 33) shows the result on the other phone within seconds; it does not change the rule.
- **Reads.** Prayers shows the phone's prayers first (the cache keeps every prayer, besides the newest 200 other entries), then the server's list (ready, tracked or answered, newest first, at most 300: `PRAYERS_LIMIT`, and `TODO`: paginate past it). Offline it is the phone's list with no error. A cached prayer the server's whole list no longer holds stops being one on the phone.
- **The mock data** (`getDataSource() === "mock"`) still runs the step 14 writes on the mock rows, with "Fail next save (dev)"; that flag does nothing to a real write.
