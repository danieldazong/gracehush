The user applies a migration by pasting the file into the dashboard's SQL editor and runs the self-tests there, which are the judge; the implementer never runs SQL against the hosted project.

The project was created with "Automatically expose new tables" OFF (Supabase makes that the default for every project on 2026-10-30; existing tables keep their grants), so the Data API cannot see a table until it is granted: every table needs explicit grants, `service_role` included (the RevenueCat webhook, `process-entry` and account deletion reach the tables through it). The v1 migration revokes first and grants back column by column, because Postgres ignores a column-level REVOKE while a table-wide GRANT exists. EXECUTE on functions is not affected by that setting.

- All schema, RLS and storage policy changes go in `supabase/migrations/` as timestamped, idempotent SQL files. Each new rule gets a check in `supabase/tests/rls_selftest.sql` and a broken variant in `run-in-pglite.mjs`; the user applies the file in the SQL editor and runs both self-tests there.
- Never edit the hosted schema by hand (the one exception was `supabase/schema.sql` in step 17, which step 18 baselined). Never disable RLS.
- Ask before creating any migration.
- **Types.** `src/types/supabase.ts` is generated from the real database and never edited by hand; regenerate it after every migration. The dashboard offers a TypeScript download at https://supabase.com/dashboard/project/_/api?page=tables-intro (it opens Integrations, Data API, Docs; the button is "Generate and download types", under the "Generating types" heading: confirmed in step 18, which used it), or, in Git Bash (PowerShell 5.1 writes UTF-16), run `npx supabase login` once and then `npx supabase gen types typescript --project-id <ref> --schema public > src/types/supabase.ts`. `src/types/database.ts` re-exports the row types and narrows what the app may send, so a write the database would refuse is a compile error.
- **What the signed-in app may write (decided in step 18).** `users_profile`: INSERT `id`, the three reminder times, `timezone`, `affirmations_enabled`, `ambient_sound` and `ambient_volume`; UPDATE the same without `id`. `journal_entries`: no INSERT and no DELETE; UPDATE `is_active_prayer`, `is_answered`, `answered_at`, `answered_notes` and `prayer_category`. `daily_affirmations`: no INSERT and no DELETE; UPDATE `is_favorite` (never `position` or `time_slot`: since 2026-11-09 the server's `feature_affirmation` moves a slot). Everything else is written by the server (`service_role`): the plan (`subscription_tier`, and since step 30 `subscription_expires_at` and `subscription_synced_at`), `is_crisis`, `processing_status`, `error_code`, the transcript, scripture, devotional and audio columns, `prayer_title` and `prayer_summary`; entries and affirmations are created only by `process-entry`. Storage: `journal_media` is private; the app reads its own folder and uploads only to `{userId}/raw/{clientEntryId}.m4a` (no overwrite, no delete); the server writes `{userId}/devotionals/{entryId}.wav` (`audio/wav`, accepted by the bucket since the migration of 2026-10-24). Deleting a reflection, with its files, is `delete-entry`'s job (step 29b), never the app's: the app still has no DELETE on `journal_entries` and no delete policy on `journal_media`, and `deleted_devotionals` is invisible to it. The `exports` bucket (step 31) has no policy at all: only `export-data` and `delete-account` (the service role) touch it, at `exports/{userId}/{exportId}.zip`, and people get a signed link.

### Schema: built in step 18, and what is still open

Built in `20261022120100_gracehush_v1_schema.sql` (these are the real names; the hand-written types of step 06 had guesses):

- `journal_entries`: `client_entry_id` (unique with `user_id`, so a retried submit never creates a second row), `processing_status` (pending, uploading, processing, ready, failed), `error_code`, `is_crisis`, `audio_path` (the raw recording), `devotional_audio_path` and `devotional_duration_ms`, `scripture_verified`, `devotional_title`, `closing_prayer`, `answered_notes` (at most 1,000 characters), `updated_at`, and the prayer fields `prayer_title`, `prayer_category` (six values) and `prayer_summary` (at most 200), and since step 36 `validation_line` (at most 240 characters, its own migration; a heavy moment has one too since 2026-11-08), and since 2026-11-11 `help_line` (the help line a heavy moment shows, one of four words, migration 13). There is no `devotional_audio_url`: no public URL was ever stored, so nothing is deprecated or backfilled.
- Rules in the table itself: a prayer is answered on a date and only then (`answered_fields_match`, `answered_note_length`: the rules prompt 29 proposed, built here while the table is empty); verified scripture has its reference and its text (`scripture_verified_check`); an entry has one affirmation per slot, owned by the entry's user. Until the heavy-moments migration of 2026-11-08 a crisis entry also had no devotional, audio, scripture, prayer, validation line or affirmations (`journal_entries_crisis_check`, `crisis_not_prayer`, `validation_line_crisis` and a trigger); those rules are gone.
- `users_profile`: `timezone`, `ambient_sound`, `ambient_volume`, `affirmations_enabled`, `updated_at`. Onboarding completion stays on the device and the devotional voice is one server-side setting, so neither is a column.
- `daily_affirmations`: `is_favorite`, `is_delivered` and `scheduled_for`. The app can write only `is_favorite`. `scheduled_for` and `is_delivered` are unused since step 28: the phone schedules the affirmation notifications itself and the server sets neither. A later migration may drop them. Since 2026-11-09 `position` (1 to 10, unique per entry, filled by a trigger when an insert leaves it out) and a nullable `time_slot` (unique per entry where it is not null): the three slotted affirmations are the lock-screen set, and an added one has no slot until the server moves one onto it.

Still open: `prayer_title` is written by `process-entry` since step 19 (the Gemini schema asks for a prayer title, a summary and a category); the `embedding VECTOR(768)` column and spiritual memory are **V2**, do not build them unless asked.
